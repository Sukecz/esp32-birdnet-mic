# Firmware 2.04 validation — 2026-10-31

This release combines continuous browser Listen scheduling and preview overflow
recovery that preserves already queued PCM. It retains the 2.03 Recording
allocation policy, Wi-Fi password editor and recovery behavior.

## Resource and regression checks

Preview storage remains 16 KiB internal on C3/C6 and 32 KiB PSRAM with the existing
internal fallback on S3/C5. There is no new heap allocation or task. Compared
with 2.03, build-reported static globals grow by 16 bytes on C3/C6 and are unchanged
on S3/C5. Capture never waits for preview sending. SD and RTSP storage are unchanged.
The larger jitter reserve is in the browser, starting at 500 ms and growing up
to 1.5 seconds after starvation. Exceptional backlog remains bounded.

Tests execute the production Recording allocation and preview sender. Coverage
includes low internal heap with PSRAM, cold SD worker overhead, allocation
failures and retries, capture/mode transitions, full preview queues, odd partial
TCP writes, slow/dead readers and concurrent rejected-byte accounting. The new
browser regression checks contiguous PCM and exact samples at 8/44.1/48/192 kHz,
600 ms coalesced reads, starvation recovery and bounded backlog.

`listen_preview_discarded_bytes` now counts rejected producer bytes, rather than
only the extra backlog previously flushed by the consumer. Historical and new
counter values are not equivalent measures of total audio loss.

## Physical and browser validation

Development C6 tests measured 16 inserted browser gaps in 90 seconds with the
old player. After both changes, a 120-second actual-device browser run had zero
inserted gaps, underruns, resyncs, frontend discarded samples, device preview
overflows or browser errors. The second half included 120 ms main-thread stalls
every two seconds, with concurrent RTSP streaming. An earlier player-only
180-second run also had zero gaps. The maintainer reported substantially smoother
sound. These short runs are not long-term network or hardware qualification.

A deliberately constrained/paused TCP reader triggered real overflow and resumed
without I2S/DMA errors or a send timeout. Long receiver stalls still lose newly
captured audio when the finite queue fills. Already captured queued PCM is now
retained, with order and partial-sample alignment checked by socket regressions.

Source and embedded UI were checked in Chromium at 320/390/1280 px, light/dark,
including retry/recovery/cancellation, volume, typography and horizontal overflow.
No persistent controls or settings lifecycle were added or changed.

## Hardware limits

The C6 test assembly has a microphone but no qualified SD module. Recording-memory
regressions are automated production-code tests, not proof of actual SD writes
or battery endurance. No other board was flashed in this release run. C3/S3/C5
builds and host tests do not qualify their physical audio or recording behavior.
Sense remains experimental. Finite preview buffering cannot prevent all loss
during extended network stalls.

## Final configured C6 OTA

The final 2.04 C6 app was installed locally. All 57 compared settings survived,
including External antenna; microphone, I2S/DMA, confirmed NTP, UTC accuracy and
local offset checks passed. The device serves the exact tested embedded UI.

A 60-second actual-device browser run (second half with 120 ms main-thread stalls
every two seconds) had zero inserted scheduling gaps, frontend underruns,
resyncs, discarded frontend samples or JavaScript errors. The device did reject
8,192 bytes of incoming PCM in eight consumer overflow observations (about 85 ms
at 48 kHz), so this is not a claim of lossless capture-to-browser delivery.
The queued audio was preserved and the browser reserve did not run empty.
Concurrent RTSP stayed active. No other physical target was updated.
